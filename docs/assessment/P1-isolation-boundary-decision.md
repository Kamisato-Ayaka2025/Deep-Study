## 2. 背景：P1 到底卡在哪

### 2.1 真卡点：读边界机制内生，AppContainer 无法区分"依赖"与"无关文件"

标准 AppContainer 令牌**认可** AAP 与 ARAP 两个包级 SID，**不认可**用户 / `Users` / `Authenticated Users`（ADR-002 测量 I，证据 `artifacts/review-P1-20261014/containment-probe/`）：

| 文件 ACL 形状 | 容器内读取结果 |
|---|---|
| 交互用户 `(F)`、`BUILTIN\Users (RX)`、`Authenticated Users (RX)` | `5` 拒绝 |
| 真实 `%USERPROFILE%` / `%LOCALAPPDATA%` 内文件（继承 ACL） | `5` 拒绝 |
| 显式 `S-1-15-2-1:(R)`（AAP） | **`0` 读到** |
| 显式 `S-1-15-2-2:(R)`（ARAP） | **`0` 读到** |
| 显式的**其他**逐容器 SID | `5` 拒绝 |

而"目录外必要依赖可读"**只能**依赖同一类 ACE：`C:\Program Files`(`(x86)`) 由 Windows 默认显式授予包类读权限并可继承；本机 `D:\Qt\Tools\mingw1310_64` 的可读性来自本项目探针自己留下的那条 `S-1-15-2-2`（ADR-002 测量 K）。

**因此"依赖可读"与"拒绝一切包级授权文件"是同一个开关，在 AppContainer 内不可分开。** 这是内核语义，不是实现缺陷。

被排除的替代路径（均已实测或评估）：

- **LPAC**：去掉 AAP 但仍承认 ARAP，因此不能拒绝"一切包级授权文件"；且不加能力则无 socket、无子进程，加 `internetClient` 则外网可达（ADR-002 测量 I 对照表）。
- **受限令牌**：`CreateRestrictedToken` 组合在进程初始化即 `0xC0000022`，夹具未执行；不能把"程序跑不起来"当作隔离成功（ADR-004、TURN-20261014-007）。
- **内核文件系统过滤组件 / VM 隔离**：需要签名驱动与安装包，或需要 Windows Sandbox（Home 版不支持，ADR-004），超出首期。

### 2.2 自造卡点：网络靶子把"本机"当成了"外网"

现存产品断言（`src/StudyHarness.Runner/RunSession.cs`）：

- `tcp-egress-denied` → 目标 `listeners.Address` = `LocalAddress()`（`RunSession.cs:437`），即本机第一个 IPv4；本机实测为 **198.18.0.1**（Clash TUN 虚拟网卡）
- `tcp-egress-ipv6-denied` → 目标 **`::1`**（`RunSession.cs:381,413`）
- `Denied()` 把二者按"外网被阻断"判定（`RunSession.cs:233-236`）

这与 REQ-034"本机通信可用"直接冲突：`::1` 按定义就是本机；宿主自身接口地址也证明不了外网。**结论：网络半边不是机制失败，是靶子选择与判定口径错误。**

新写的 `probes/PsecNative/network.c` 已使用正确靶子，结果为合格的正反对照（见 §4.2）。

## 4. 决策含义

### 4.1 B1 之下的实际读范围

**可读**：带 AAP/ARAP 显式或继承 ACE 的文件。真实机器上主要是 `C:\Program Files`(`(x86)`) 整棵树（Windows 默认），以及任何安装方显式授权过的目录（本机 MinGW 即为一例）。

**不可读**：用户个人文件、StudyHarness 数据根、`Users`/`Authenticated Users` 授权文件、其他容器 SID 授权文件。

**待补实测（低成本，建议纳入 P1 收口）**：遍历本机顶层目录，列出**哪些路径带包级 ACE**，形成"容器可读范围清单"并写入 ADR。这样 B1 是"量化并接受的已知范围"，而不是"放宽了标准"；同一份清单将来可直接作为 PSEC 只读白名单的输入，也是 H9 干净环境验收的对照基线。当前只有 `Program Files` 树、`D:\Qt\Tools\mingw1310_64`（探针残留）两处有直接证据，系统目录的可读性属**推断**（进程需加载 DLL），需补测。

### 4.2 D2 之下网络验收口径的重述

- **正例（本机通信）**：改为只保留"容器自身可创建并使用 socket"这一类自证能力，或按 D2 直接取消该项。
- **负例（外网阻断）**：改用**真正的外部目标**，并保留宿主可达正对照。已有合格数据（`probes/PsecNative/network.c`，目标 `223.5.5.5:53`）：

| 观测 | 宿主 | 容器内 |
|---|---|---|
| TCP 223.5.5.5:53 | `0` 可达 | `10013` 拒绝 |
| UDP DNS 查询应答 | 收到应答 | 超时无应答 |
| 原生 IPv6 外连 `2001:4860:4860::8888:53` | **`10051` 网络不可达** | 同左 |

- **IPv6 外网**：**本机无 IPv6 出口，宿主自身即不可达**，因此无法构造正对照。首期登记为"本机环境无法验证"的覆盖缺口，不得用超时冒充证明，也不得删除该覆盖项。
- 必须删除或改写**指向 `::1` 与宿主自身接口地址的"外网"断言**——它们与"本机通信"语义冲突，且与机器网卡配置耦合（本机为 Clash TUN 的 198.18.0.1）。

### 4.3 对下游特性的影响：零功能损失

四个下游特性都不需要网络，P1 已验证的能力（隔离内编译、隔离内运行、work 内可写、目录外只读依赖、子进程、停止、整树回收）已覆盖其全部需求。宿主↔容器 IPC 本来就使用**继承的标准句柄**而非 loopback（ADR-002 决策 5；容器连宿主命名管道实测 `5`）。

| 特性 | 需要的新能力 | 受隔离限制 | 主要新增约束 |
|---|---|---|---|
| 本地 Judge（REQ-023） | 逐用例喂 stdin/参数、宿主侧捕获 stdout 与退出码、逐用例终止与比对 | 无 | 判定必须宿主侧采集；需逐用例终止策略 |
| 参考解验证（REQ-037） | 同上，代码由模型生成且无人值守自动执行 | 无机制限制 | **风险最高路径**，需额外收紧（§5.5） |

| 临时答疑（REQ-024） | 读当前实验文件并调用 DeepSeek | 无 | 属产品出口，见 §5.4 |

## 5. 安全影响与必须同时满足的前提

### 5.1 B1 + 无网络断掉的是哪条链

经典三步：**读秘密 → 外传 → 持久化**。

- 外传：断（无 socket、无 loopback）。
- 持久化：断（work 外不可写；AppContainer 无能力时注册表访问亦受限）。
- 读秘密：**部分残留**，即 B1 让渡的包级 ACE 范围。

三步只剩一步，且是不能落地的一步。该姿态的强度大致等同于 Windows 为 Store/UWP 应用提供的容器沙箱：不是"防定向攻击者"的强沙箱，但对"防止模型生成或被提示注入的代码触碰个人数据、外发、留下后门"这一目标是成立的。

**必须如实表述**：产品文案与文档应说明"实验代码在受限容器中运行，读不到你的个人文件，也没有网络"，**不得声称"完全沙箱"**。

### 5.2 前提一：资源上限（当前缺失，必须先补）

`src/StudyHarness.Runner/Sandbox.cs:186` 的 Job Object **只设置了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（0x2000）**；结构体中的 `ProcessMemory` / `JobMemory` / `ActiveProcessLimit` 字段存在但未设置。夹具已证明三种派生子进程方式均成功（`childSpawnStyleB/C = 0`），且 REQ-034 允许"不设自动时长上限"。

**后果**：一段代码可以 fork 炸弹或耗尽内存，使整台机器失去响应，产品无法拦截；work 目录写满磁盘同理。

**要求**：Judge 与参考解验证上线前，必须设置进程内存上限、作业内存上限与 `ActiveProcessLimit`，并为 work 目录设定容量上限或告警。

### 5.3 前提二：判定必须宿主侧采集

当前夹具把结论写入 `work/escape.json`，宿主再读取解析（`RunSession.cs:166,243`）。对固定合成夹具无妨，但**对 Judge 是危险模式**：被执行的程序可以伪造自己的成绩单。

**要求**：通过/失败只能来自宿主通过继承句柄捕获的 stdout 与退出码；**不得采信容器内程序写出的任何判定文件**。

### 5.4 前提三：出口约束（唯一未被覆盖的外泄路径）

REQ-034 明确允许产品调用 DeepSeek。若**运行输出**或容器可读到的内容进入模型请求，则 B1 的读范围就变成外泄范围（链路：模型生成代码读 `Program Files` → 打印到 stdout → Judge 反馈/答疑带上 → 发往 API）。

**要求**：写入 P4/P6 的契约——发往模型的内容只限用户自己的实验源码、用例输入/期望/实际输出等**派生自 work 且有长度上限**的内容；不得透传任意文件内容或未裁剪的运行输出。

### 5.5 前提四：参考解验证单独收紧

REQ-037 是唯一"模型生成代码自动执行、用户未看过即运行"的路径，而导入的 PDF/Markdown 是提示注入入口。B1 之下**无法**为它单独收窄读范围（这正是 B1 的代价）。可用的缓解措施：

- 无网络 + work 外不可写（已有）；
- 资源上限（§5.2，待补）；
- 在**独立 run 目录**中执行，不复用用户工作目录；
- "验证通过"必须绑定一条真实运行记录，不以模型自述代替（REQ-037 原文要求）；
- **若将来引入 PSEC，参考解验证应是最先迁移的路径**，届时读范围才可收窄。

### 5.6 其他应当在 ADR 中登记的未验证面

以下属于"已知未验证"而非"已知安全"，首期不得沉默略过：

- 注册表读写、命名对象（全局事件/互斥体）、剪切板、COM/RPC 进程外激活、向其他进程发送窗口消息；
- 符号链接（本机缺 `SeCreateSymbolicLinkPrivilege`，仅有 junction 覆盖）；
- 同一容器内并发运行、长期运行的资源漂移；
- work 目录是**容器→宿主的写通道**：容器可在其中创建 junction（无需特权），因此宿主读取运行产物与递归清理时都必须解析最终路径并拒绝重解析点（Plan §6.5 已对"递归写/删除"提出此要求，对"读取产物"同样适用）；
- 被强杀的 Runner 会留下孤儿 AppContainer profile 目录及其失效 SID 的 ACE，建议增加启动期清理。

### 5.7 两点既有设计的肯定

- `SandboxProfile.Create(profileId + "." + Guid)`（`Program.cs:148`）为每次运行生成独立 SID，`Dispose` 删除 profile，因此**不存在跨运行经复用 SID 读取旧 work 目录的问题**。
- 容器环境块为显式白名单构造而非整体继承（ADR-002 决策 4），宿主环境中的密钥类变量不进入容器。

- **网络取舍**：PSEC 允许 loopback 就会同时打开宿主本机监听与本地代理可达，与"外网阻断"冲突；MXC 自身的建议模型是把 egress 收窄到指定 loopback endpoint（Model 2）。即**换成 PSEC 会把网络半边从基本成立变成需要重新划线**。
- **契约风险**：MXC 的 containment policy `1.1.0-alpha` 标记为 Development/mutable，`1.0.0` 才是 current stable；产品需自行编码 spec 并做版本协商，不可用时必须 fail-closed。
